## TARAflow 0.18.0-beta

More of your requirement matrices straight from the model, EN 50742 Approach A as a matrix of its own, Azure DevOps and four more issue trackers — and an AND gate in an attack tree is finally one attack scenario.

> New project schema **13** — a project is converted when it is opened (a backup of the original is written next to it) and then no longer opens in 0.17.x. A TARA verification stays valid, except for projects whose attack trees contain an AND gate (see below).

### Requirement matrices from the model

- **New model fields** on processes, multiprocesses and data flows — accounts, password rules, role mapping, default credentials, login lockout, update delivery, secure by default, deletion of user data, access mode, data minimisation. Each appears only where your earlier settings make it meaningful. More IEC 62443-4-2 rows are now derived instead of asking for a statement.
- **Security in sub-tabs:** the Security section of processes and multiprocesses is split into Login & accounts, Authorization, Communication, Robustness, Sessions & traceability, Operation and Data; each tab tells you how many fields are still open. Safety stays below the tabs.
- **Secure channel** instead of "TLS termination": an endpoint names every channel it offers — TLS, mutual TLS, VPN, SSH, application-level security — and a flow's encryption is checked against its endpoints (SSH needs one end offering it, application level both). A channel no flow uses and a network or fieldbus element without a channel are reported in the DFD findings.
- **Update package encryption** and **key renewal** as model fields; "Exposed to Internet" of a process moved to its context.
- **Black boxes:** a multiprocess without a child page — a PLC drawn as a box, a supplier's communication module — summarises what it contains in seven *Inside* fields, and the matrix checks it like the processes and data stores it stands for.
- **Claims for the system around the component:** a requirement the plant provides is covered by a supporting claim; it counts for the value with measures of the system, never for the product's SL-C.
- **Project mitigations** say which IEC 62443-4-2 requirements they implement.
- **Compliance tab:** "Unknown" is now **Information missing** and names the empty field per element ("information missing on MP-1 (password lifetime limit)"). A row met by a statement while the model is still open says so. Rows an edition declares void link to a dialog with the reason. Supporting claims no requirement uses any more can be deleted.
- **Report:** the table *Gaps against the SL-T* gives the catalog mitigations with their text, not only their id.

### EN 50742 Approach A

- With the EN 50742 A tag the Compliance tab shows the **23 baseline requirements** next to the IEC 62443 editions — checked against the model, the risks (SRSL, mandated §7.4.3 controls) and the project data.
- The header shows the **highest SRSL per safety function** and the **interfaces on the path** to it, derived from the DFD; a data diode ends the path.
- The report has a part for EN 50742 A in the requirement matrix chapter — one part per active standard.

### Issue trackers

- **Azure DevOps** (Azure Boards): create and link work items, follow their state — the token is bound to your organization and stays in the OS keychain.
- In **preview** — usable now, confirmed against live instances over time: **Jira Server / Data Center, GitHub Issues, GitLab Issues, OpenProject**. Polarion follows later.

### Attack trees and threats

- **An AND gate is one attack path** per combination of its steps, rated with the gate's feasibility over exactly those steps. Before, every step became a threat and a risk of its own.
- **Threat generation no longer trusts a gap:** a catalog condition on a missing or weak control also matches when the property is not set yet — an unfinished model no longer looks safer than a complete one.
- After renaming an attack-tree node, **Goals & Claims** offers to re-link the goal or claim to the renamed path.

### Also new

- **Asset tab filter** by asset type (a dropdown to tick and untick the types) and criticality ("from level"), across all groups; the filter bar looks like the risk tab's.
- **Description view:** create an asset by name and category right there, link it to elements later.
- **Asset graph:** three rows per category lane (and in the free rows) to align assets; *Rearrange* spreads a crowded category over its rows by the asset's links, so fewer lines cross. A relation filter (checkboxes for DFD element, asset and hazard relations) shows what is still to be linked; the graph shows only the hazards marked relevant (in scope).
- **Hazard tab findings panel** below the table; a click opens the hazard.
- **Report:** rejected mitigations appear with their reason.
- Risk levels and colours follow your **own severity thresholds** everywhere, and the risk matrix cells agree with the risk chips.
- Risk and hazard messages in **German** too.
- Audit commits check out the branch before staging; saves after a project switch land in the right project.

### What you should do

1. Open your projects in 0.18 — they are converted to schema 13 (backup alongside).
2. **Attack trees with an AND gate:** the conversion merges the former leaf paths into one path per combination. Check the risks of these trees — each says in its justification where it came from, and *review the rating and the treatment* where the old ratings differed or a step had none — look at the old assessments the attack-tree banner shows, and confirm the TARA verification again.
3. **Secure channel:** a former TLS termination is carried over as a selection of one. Open the DFD findings — a network or fieldbus element without a channel and a channel no flow uses are listed; set *None* where there is deliberately none.
4. **Compliance tab:** filter *Information missing* — each row names the field still empty; filling it lets the model decide the row.
5. Regenerating threats may switch a few templates to the variant for the missing control where a property is unset — set the property and the specific template comes back.
6. Azure DevOps users: in Integration choose Azure DevOps, enter `https://dev.azure.com/<organization>` and a PAT with *Work Items: read & write*.
