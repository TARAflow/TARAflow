## TARAflow 0.19.0-beta

Analyse a component once, use it in every machine: the TARA of a reused component — a sensor, a controller, a supplier's module — is now imported into the TARA of the machine that contains it, pinned to a commit of the component's repository, instead of being analysed again.

> New project schema **14** — a project is converted when it is opened (a backup of the original is written next to it) and then no longer opens in 0.18.x. A project without imported components changes in nothing else, and a TARA verification stays valid.

### Component TARAs in a machine TARA

- **Import component TARA…** in the DFD tab: pick the component's committed `.tara.json`, choose the commit or tag, map the component's external entities to elements of your machine. The component appears as a multiprocess with its DFD on read-only pages and its boundaries around it. Several instances of one component get their own prefix (*SD1*, *SD2*); identical units in the same place can be one instance with a quantity.
- **What comes with it:** threats, attack trees, intrinsic factors, measures, assets and their relations, assumptions of use, supporting claims and the component's overview. **Never** its impact, context factors, risk levels or hazards — those depend on your machine.
- **What you decide per instance:** the impact of the instance's assets, the context factors, the window of opportunity of each attack path (also per step of an AND combination), whether a threat on a flow across the component's boundary is relevant here (with a rationale), and the component's **assumptions of use** as a checklist — fulfilled, not fulfilled or not applicable, with your evidence. Ratings can be copied from another instance once.
- **Component measures count only while they hold:** a measure of the component lowers your risk only while the component implemented it and every assumption it relies on is fulfilled in the instance with implemented evidence. Otherwise it is *unclear* or *not effective*, and the risk is shown with its value before treatment. The same rule decides whether it is evidence in the requirement matrix. You can also mark a component measure *not effective here*.
- **A newer component state:** *Check* (or *Fetch and check*) tells you whether the component moved on. *Update…* shows what changed, which of your decisions are affected, new external entities to map and threats or paths to pair with their predecessors — and says so when no decision is affected. *Discard update* goes back until you save.
- **Overview tab *Components*** (while something is imported): where each component comes from, its instances and assumptions, the drift status, and the **deviations** — what your TARA decided differently from the component. Copy them as Markdown for the component's team.
- **Report:** the imported threats and risks with their origin, the imported attack trees with every attack-potential factor per step, and a chapter *Imported components* — in every format including the PDF.
- **Audit:** the Audit Verification Engine checks that every imported component in a committed file still matches its recorded snapshot (new check *component-import*, results now `aveVersion: 2`). The commit diff names instance changes in words.

### Also new

- **Issue trackers:** one ticket row per mitigation with a link dialog — search, status filter, suggestions — or *create*; with a linked ticket the progress follows the ticket. In a project with a tracker, a mitigation set to done by hand asks for evidence or a reference.
- **Audit commits** name the TARA file in the subject and in a `Project-File` trailer — useful with several TARA files in one repository.
- **Compliance tab and report:** the to-do list uses the labels of the DFD form and names only the fields still unset; status reasons and missing fields appear in the document language.
- **Asset group fields** (data type, lifecycle, exposure, role, …) are now asked for as an *info* and say what they are used for; a DFD can be *complete* without them.

### Removed

- **Protection need and criticality** of an asset: ratings no calculation used, which could contradict the security goals and damage scenarios that threats, risks, compliance and the report actually use. Some other unused asset fields without an input are removed with them.

### Fixed

- A risk is *verified* only when **every** active mitigation is verified.
- Multi-page DFDs no longer lose their page tree after a project switch (no more *Adopt pages* on every page).
- An autosave no longer replaces a change made while the project was being written.
- *Open project* starts in the folder of the open project.
- The CLI report shows MoSCoW, impact, STRIDE and status labels again.
- Repository URLs are stored without credentials.

### What you should do

1. Open your projects in 0.19 — they are converted to schema 14 (backup alongside).
2. **Check the risk overview before an audit:** risks with one mitigation still only implemented fall back from *verified* to *implemented*.
3. **Protection need and criticality** are dropped when a project is opened; the first commit diff lists them once. Your verification stays valid.
4. **Flows between two external entities:** the next threat regeneration removes their per-element threats, and the risk sync then removes the risks with their ratings and mitigations. If such a flow matters, model one side as a process first.
5. **Leveled DFDs where you confirmed *Adopt pages* after a project switch** (0.14 – 0.18): check the context copies and the page tree.
6. **A source URL with a token in it** is now flagged. Remove it — and revoke the token at the provider, because it stays in the git history.
7. **CI with `taraflow-verify`:** results carry `aveVersion: 2`; adjust a pipeline that checks the version or compares with stored results.
8. To import a component, **commit its TARA first** — an uncommitted file is imported *unpinned*; once committed, *Check* offers *Refresh stored state…* to pin it. The drift check needs a local clone of the component's repository.
