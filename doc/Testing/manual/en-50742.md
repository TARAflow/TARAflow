# Manual test: EN 50742 Approaches A and B

## Purpose

This guide tests the EN 50742 support of 0.20 by hand:

- the tag rules: one base method, Approach A as an addition, exclusions;
- the safety zone and the EL badges in the diagram;
- the EN 50742 relevance of risks;
- Approach A with the standard method and with ETSI TVRA;
- Approach B and its requirement matrix;
- the report.

Run it before every release that touches EN 50742, the tag editor, the DFD badges or
the risk calculation.

The two example projects of the examples repository are generated by code, see
[The examples](#9-the-examples). Mark every step **OK** or **Deviation**
(see [Reporting](#reporting)).

## Prerequisites

- TARAflow desktop app (Electron) or the browser build.
- The `TARAflow_Examples` repository checked out.

### Test data

Start from `TARAflow_Examples/Simple_Test_Project.tara.json`. Copy it to
`EN50742-A-SafetyZone.tara.json`, and work only on the copy.

| Element | What it is |
|---|---|
| `MTB` My Trust Boundary | Trust boundary, default EL1. Becomes the safety zone. |
| `IF-1` USB, `IF-2` JTAG | Interfaces, EL1 |
| `DB` Device Boundary | Physical boundary, PEL2 |
| `STM` STM32F4 | Chip boundary, default EL1 |
| `P-1` MyProcess, `DS-1` Flash | Process and store inside `MTB` |
| `EE-1` MyExternal, `EE-2` Debugger | External entities |
| `DF-3` push control command (EE-1 → P-1), `DF-2` write config data (P-1 → DS-1), `DF-4` push register data (EE-2 → STM) | Data flows |

The project has the tags *IEC 62443* and *EN 50742 A* and the window of opportunity
*moderately restricted*.

|---|---|---|

| 1.2 | Add *ISO 21434*. | *ISO 21434* replaces *ETSI TVRA* and *EN 50742 A*. A blue line names both. |
| 1.3 | Cancel the edit. | The tags are as before. |
| 1.4 | Add *EN 50742 B*. | B replaces A. The blue line says "EN 50742 B replaces EN 50742 A". *IEC 62443* stays and is not added twice. |
| 1.5 | Cancel. Type the free tag `EN 50742` and press Enter. | Not added. The blue line asks to choose A or B. |
| 1.6 | Type `EN50742_A` and press Enter. | Nothing changes: *EN 50742 A* is already there. |
| 1.7 | In a scratch project: add *EN 50742 B*, then remove *IEC 62443*. | An amber hint says that B needs an IEC 62443-4-2 edition. Adding *EN IEC 62443 (CRA)* removes the hint. |

Cancel the edit, so the copy keeps *IEC 62443* + *EN 50742 A*.

## 9. The examples

The two example projects of the examples repository are generated by code, from the
same model (`src/tests/examples/en50742-examples.ts`, base: the Simple Test Project
without its tracker and audit settings). `en50742-examples.test.ts` checks what they
promise through the results dump; with `WRITE_EXAMPLES` it writes them:

```
WRITE_EXAMPLES=../TARAflow_Examples/en50742 npx vitest run src/tests/examples/en50742-examples.test.ts
```

| File | Content |
|---|---|
| `en50742/EN50742-A-SafetyZone.tara.json` | Approach A, standard method, safety zone `MTB`: the risks of `DF-3` and the attack path get EL, AC and an SRSL, the others L × I only; `DS-1` keeps the audit records, but no relevant flow reaches it — row 7.3.4 names why |
| `en50742/EN50742-B-SafetyZone.tara.json` | Approach B on the same model, with IEC 62443: embedded device (EDR), IEC 62443 target as the fixed SL-T of Table 4, standard factors, no SRSL |

Every risk is rated; *reduce* risks have their first two catalog proposals planned.
After a run of this test without deviations, open both files once in the app: nothing
may change (no unsaved changes, no sync banner). Then commit them in the examples
repository and add them to its `README.md` overview table. The results dump reference
gets them in the next release folder of `doc/Testing/results-dump/`.
